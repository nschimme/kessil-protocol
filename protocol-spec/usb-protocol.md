# Kessil Spectral Controller X USB protocol notes

The Controller X host interface and fixture-facing K-Link interface are separate. Kessil identifies Micro-USB as the firmware-update port and K-Link as the light connection ([controller page](https://kessil.com/products/accessories_SpectralControllerX.php), [quick-start manual](https://kessil.com/downloads/accessories/5870124%20A3%20User%20Manual%20for%20Spectral%20Controller%20X.pdf)). For the legacy network API, see [WiFi Dongle notes](wifi-dongle-protocol.md); for the AP700 discussion, see [the AP700 reference](ap700-protocol.md).

## USB interface summary

Static analysis of a Controller X updater identifies a USB device filter with VID `C251` and PID `2201`, and fixed 65-byte request/response buffers. These likely map to HID reports, but no live report descriptor or exchange was captured. The update flow involves separate image and application-firmware transfers; its framing alone does not establish device-side acceptance or integrity checks.

This publication omits firmware acquisition, extraction, and flashing workflows. No update has been attempted or validated on hardware. The [firmware update summary](firmware-update.md) distinguishes the product-specific interfaces.

## K-Link serial protocol found in the firmware

The firmware does contain protocol details beyond USB updating. Ghidra analysis identifies an LPC17xx UART driver and an initialization path named `test_Uart2Init`. Its default UART configuration structure sets baud rate to `0x1c200` (115200); UART2 is enabled and used to transmit/receive framed messages. This is strong evidence for the controller-side K-Link transport, though the exact physical pin mapping and electrical levels still need board or capture confirmation.

The firmware's parser recognizes frames with this layout (byte offsets are relative to the `D7` marker):

| Offset | Meaning |
|---:|---|
| 0 | Start marker `D7` |
| 1 | Length, bounded by the parser (`< 0x1e`; the separate frame validator accepts only `< 9`) |
| 2 | Uninterpreted header byte (the dispatch path ignores it) |
| 3 | Reserved byte, required to be `00` by the dispatch path |
| 4 | Command/opcode byte used to select the handler |
| 5 onward | Command data |
| `length + 1` | Additive checksum; sum from length through the final data byte is negated modulo 256 |
| `length + 2` | Terminator `5C` |

Byte 2 has no recovered semantic meaning in this receive path. The recovered D7 dispatch routine does not read it: after frame validation, the routine requires byte 3 to be zero, then matches byte 4 and the frame length against a handler table. Byte 4 is therefore the observed command/opcode field; no evidence shows that byte 2 selects a lamp or acts as an address. Do not confuse either field with `D7`, which is the frame marker. The parser passes a buffer pointer one byte before the marker to its frame validator; that validator therefore sees `D7` at pointer offset 1, while the handler reads the marker-relative layout shown above. A separate validator receives the marker at offset 0 and checks a caller-supplied expected byte at offset 2, so it is a different validation path rather than evidence for another field in the dispatch frame. Separately, the [AP9X STM reply serializer](klink-protocol.md#independent-confirmation-in-ap9x-firmware) also places its command at byte 4 and has separate fields at bytes 2–3; that supports the command-vs-other-fields distinction only for the AP9X `A9` path and does not resolve Controller X's `D7` byte 2.

The UART transmit routines construct frames beginning with `A9`, append a length, fields, the same two's-complement additive checksum, and `5C`. The Controller X `1F` path (`FUN_00001534`) computes five channel bytes into offsets 5–9, writes a one-based selector (`index + 1`) at offset 10, sets offset 11 to zero, and transmits a frame with length `0B`. Its recovered caller `FUN_0000174a` walks up to 32 lamp records and invokes `FUN_00001706` for each active record; `FUN_00001706` passes that record's array index to the `1F` builder. Thus the Controller X selector is tied to its local lamp-record index plus one. This `1F` frame matches the Dongle/AP9X layout of five channel values, selector, and trailing `00`, which is consistent with a group-level manual-control frame. However, Dongle/AP9X builders serialize the raw GID, and no Controller X mapping from its record index to a GID or fixture address was recovered. Do not assume equal selector values address the same fixture across the Controller X and Dongle/AP9X paths. In this Controller X path, the first two source values are multiplied by 255, converted to software floating point, multiplied by the IEEE-754 constant `0.01` stored at `0x18A0`, then converted to integers; for nonnegative inputs this yields `floor(value × 255 / 100)`. Their order is swapped on the wire: source byte 1 becomes frame offset 5 and source byte 0 becomes offset 6. The other three source values are copied directly to offsets 7–9. The wire layout therefore matches the Dongle/AP9X group frame, while the value scaling and first-two-value ordering are not identical in the recovered builders. The exact channel names and model-specific mapping remain unknown. Command `11` is built by `FUN_0000160a` as a length-`0A` frame with six payload bytes at offsets 5–10. The builder reads a program-point record from a table (`base + index*0x93 + point*0x0D`) and selects one of two layouts using its third argument: the first layout reads six source bytes beginning at record offset `0x12`, scales source bytes 1 and 0 into offsets 5 and 6 respectively, copies source bytes 2, 3, and 4 to output offsets 7, 8, and 9 respectively, leaves source byte 5 unused, and writes zero to offset 10; the second reads four source bytes at offset `0x18`, scales source bytes 1 and 0 into offsets 5 and 6, writes zero at offset 7, copies source bytes 3 and 2 to offsets 8–9, and writes one at offset 10. Both layouts then transmit through the same `A9` command-`11` framing helper. Call sites show both layouts are reachable: `FUN_00009d56` and `FUN_0000a20c` pass `0`; `FUN_0000ab7c` passes `1`; and `FUN_00009b88` passes `1` in one branch or reads a byte at `program_index * 0x93 + 0x90` in another. These callers establish observed sources for the builder argument, not its meaning. `FUN_00001706` is not a command-`11` caller; it invokes the separate command-`1F` builder `FUN_00001534`. Overall, the builder establishes the frame shape, value scaling, and table data flow, but not the mode meaning, source-field semantics, or device-side effect; no live response was captured. Caller analysis adds a limited edit-path clue: `FUN_00009d56` changes one selected point byte at the caller-side table offset `3 + index`, increments/decrements it by one with a 0–100 clamp, then calls the layout-0 builder, which separately reads six bytes beginning at source offset `0x12`. `FUN_0000ab7c` sends layout 1; for selected point indexes 0 and 1 its caller updates the program time with hour/minute wrap at 24/60, while indexes 2 and above edit a separate point byte with the same one-step 0–100 clamp. This describes the Controller X UI-side source mutations, not the meaning of command-11 wire fields: the relevant point/time tables are distinct, and no captured exchange links them to fixture behavior. The concrete layout below makes the recovered byte mapping explicit; both examples use synthetic source bytes, not a captured K-Link exchange. The checksum covers bytes 1–10, so the sum of those bytes and the checksum is zero modulo 256.

For layout 0, synthetic source bytes `14 50 0C 22 38 44` at offset `0x12` produce `A9 0A 00 00 11 CC 33 0C 22 38 00 80 5C`: source bytes 1 and 0 become `CC` and `33` after scaling; bytes 2–4 are copied; byte 5 is omitted. For layout 1, synthetic source bytes `14 50 0C 22` at offset `0x18` produce `A9 0A 00 00 11 CC 33 00 22 0C 01 B7 5C`: output offset 7 is zero, source bytes 3 and 2 become offsets 8 and 9, and offset 10 is one. These examples demonstrate only the builder's serialization.

The query builders for commands `19`, `1C`, and `35` each place a 32-bit big-endian KID in the frame. The receive dispatcher recognizes command `19`: it reads a 32-bit big-endian identifier from command data, sends an `A9` command-`19` frame containing that same identifier, and appends the identifier to an in-memory lamp list capped at 32 entries. For KID `0x0112A880`, the A9 command-`19` transmit template is:

```text
Command 19: A9 08 00 00 19 01 12 A8 80 A4 5C
Command 1C: A9 08 00 00 1C 01 12 A8 80 A1 5C
Command 35: A9 08 00 00 35 01 12 A8 80 88 5C
```

The `D7` command-`19` receive frame has the same length and KID fields but uses the `D7` marker; if byte 2 is zero, the example is `D7 08 00 00 19 01 12 A8 80 A4 5C`. Byte 2 is included in the checksum but is not read by the recovered dispatcher or handler. Caller code gives these KID-bearing requests the following observable behavior:

| Command | Caller-observed use | Wait/retry behavior | What remains unknown |
|---:|---|---|---|
| `19` | Receive handler reads the big-endian KID, echoes it in an `A9` command-`19` transmission, and appends it to a lamp list capped at 32 entries. | The receive handler's own path is recovered; a general retry policy is not established. | Whether the echoed frame is a protocol acknowledgment and whether the received byte-2 field has any meaning. |
| `1C` | The lamp-record routine issues this request per KID and stores two response bytes in that lamp's record. The builder is named `GetAll`; another builder named `GetGid` emits the same request frame. | `FUN_000140cc` waits up to 1 s for receive frames; the caller initializes two result slots to `FF` and retries the query up to five times while either remains unset. | The two response-byte meanings and exact response frame schema. |
| `35` | A separate routine issues this request with a KID and stores one response byte in an indexed array. | The caller retries up to five times while its result remains `FF`; the shared wrapper waits up to 1 s per query. | The result-byte meaning and exact response frame schema. |

The request builders establish the KID encoding and frame bytes shown above, while the callers establish query/reply behavior. The command-`19` receive path appends KIDs to an in-memory lamp list capped at 32 entries, while the `1F` caller separately walks up to 32 lamp records. The shared limit is not evidence these are the same table or that record index `n` corresponds to the nth discovered KID; no caller mapping between the structures was recovered. The response handlers that populate the `1C` and `35` result slots were not resolved, so those results should not be interpreted as a specific GID, status, or firmware value. The dispatch routine dereferences its handler-table pointer from `DAT_00013bc8`; the extracted `FW.bin` stores `0x00017594` there, beyond the file's `0x160dc`-byte extent. The related callback-count pointer at `DAT_00013bcc` points into `0x1000xxxx` RAM. Therefore the supplied application blob does not contain the runtime dispatch table in the analyzed address range, and the unresolved `1C`/`35` callbacks cannot be reconstructed from this file alone; this does not prove they are absent from the running device. In the raw image loaded at base address zero, the relevant Ghidra functions are `FUN_00013950` (D7 frame validation), `FUN_000139a0` (dispatch and KID list), `FUN_00013a3a` (checksum), `FUN_00013a5c` (command 19), `FUN_00013d88` (command 1F frame transmission), `FUN_00013e64` (command 1C), `FUN_00013fc4` (command 35), `FUN_000140cc` (query/wait wrapper), `FUN_00001534` (command 1F payload construction), and `FUN_0000160a` (command 11 payload construction). Its `A9` transmit frame and `D7` receive frame must be interpreted independently; shared command numbers do not prove byte-for-byte framing equivalence with the Dongle/AP9X `A9` protocol.

The firmware contains K-Link framing, KID-based queries, a KID announcement and echo path, and a group-level `1F` manual-control frame matching the Dongle/AP9X layout. It still does not provide a complete light-control command map. Command `11`'s frame construction, program-point inputs, and conversion scale are partly recovered above, but its mode parameter, source-field semantics, and device-side effect remain unknown. The semantics (if any) of the receive frame's ignored byte 2, channel names, and meanings of most responses need more analysis; a captured UART exchange would validate their interpretation.

The separate WiFi Dongle path also needs to account for multi-light K-Link. The owner reports two Tuna Sun fixtures daisy-chained with a standard USB-C cable, with the Dongle plugged into one fixture; see [the topology and multi-lamp command notes](klink-protocol.md#two-light-k-link-topology-reported-by-the-owner). The Dongle firmware's explicit `A9` K-Link frame builders are now documented in [the Dongle-to-light frame reference](klink-protocol.md#dongle-to-light-k-link-uart-frames). The Controller X firmware has a distinct `D7` receive-parser path, so do not assume it shares the Dongle's frame format without comparing an actual Controller X/light exchange.

## What this establishes, and what remains open

The updater reveals the Controller X USB update protocol; the embedded application firmware additionally reveals a UART-based framed protocol with `D7` receive and `A9` transmit markers, additive checksums, command dispatch, and a lamp-list/identifier path. The official connector documentation identifies the controller-to-light connection as K-Link and Micro-USB as the firmware-update port. So firmware analysis is directly relevant to the goal, even though the K-Link command semantics and physical UART details need further validation.

The USB VID/PID remains an updater filter not cross-checked against a live descriptor. The Controller X frame offsets above are now reconciled across the dispatch validator and handler; the separate expected-byte validator is not used as the dispatch frame layout. Command semantics, physical UART pin mapping/electrical levels, and actual Controller X/light interoperability still need a read-only capture.
