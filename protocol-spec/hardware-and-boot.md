# Hardware and boot-chain notes

This page records hardware and startup details that can be inferred from the analyzed firmware and updater artifacts. It distinguishes boot integrity (whether code is authenticated before execution) from readout protection (whether a debugger can copy code) and update checksums (whether a transfer is corrupted). Exact board revisions and fuse/option settings of physical Kessil products are not available in these artifacts.

## What “secure boot” means here

For this project, call boot authenticated only when we can show a trust anchor and a signature/MAC verification that runs before candidate code executes, with the verification key protected from replacement. A CRC, MD5 comparison, USB report checksum, readout lock, or encrypted transport alone does not meet that bar. U-Boot distinguishes its legacy image format from signed FIT verified boot; legacy image support is described as limited and insecure ([U-Boot `bootm` documentation](https://docs.u-boot.org/en/latest/usage/cmd/bootm.html), [FIT signature verification](https://docs.u-boot.org/en/latest/usage/fit/signature.html)).

## Evidence and limits

- Dongle rootfs: `/etc/openwrt_release` specifies `ramips/mt7688`; LinkIt service files say `LinkIt Smart7688`; board scripts include `linkits7688`; `/lib/modules/3.18.109/mt_wifi.ko` and `/etc/Wireless/mt7628_tpl.dat` identify the supplied Wi-Fi driver/profile. No Bluetooth-named module or stack was found. Publication scope and the update-interface summary are in [`firmware/README.md`](../firmware/README.md) and [`firmware-update.md`](firmware-update.md).
- Dongle wireless setup: `/etc/uci-defaults/51_linkit_config` reads `wifi_ssid` and `wifi_seq` from the boot environment, falls back to the serial as SSID, reverses the SSID for the AP key, and sets `wireless.ap.encryption='psk2'`; although it reads `wifi_key`, the block that would use that value is commented out. The `/lib/wifi/ralink.sh` template identifies the `11ng`/HT20 profile. `/bin/ap_to_sta` stores the app-provided station `SSID`, `PWD`, and `ENC`. These are the bundled 1.5.13 software defaults; runtime settings and negotiated radio security were not captured.
- AP9X module header identifies OpenWrt Linux/MIPS and LZMA; its extracted SquashFS `/etc/kernel.config` sets `CONFIG_RALINK_MT7628=y`, `CONFIG_SECOND_IF_MT7663E=y`, `CONFIG_WIFI_MT7663E=y`, and `CONFIG_CHIP_MT7663E=y`. The rootfs contains `/etc/wireless/mt7628/` and `/etc/wireless/mt7663/` profiles plus `/lib/wifi/mt7628.lua` and `/lib/wifi/mt7663.lua`. It sets `# CONFIG_BT is not set`. These are firmware-build/configuration facts, not a hardware teardown. The checks described above are software-analysis findings; see [the update-interface scope](firmware-update.md).
- The AP9X STM hardware and update observations are summarized in the device inventory above. ST describes RDP as configurable flash readout protection, which must be set on-device and is not equivalent to secure boot ([ST AN5156](https://www.st.com/content/st_com/en/technical-documents/an5156-introduction-to-security-for-stm32-mcus-stmicroelectronics.html), [ST AN4758 for STM32L4](https://www.st.com/resource/en/application_note/dm00226247-proprietary-code-readout-protection-on-stm32l4-stm32l4-and-stm32g4-series-microcontrollers-stmicroelectronics.pdf)).
- Controller X updater and firmware evidence is in [`usb-protocol.md`](usb-protocol.md). NXP documents LPC Code Read Protection as access/read restrictions; it is not firmware-signature verification ([LPC1768 product page and linked user manual](https://www.nxp.com/products/LPC1768UK)).
- The AP700 is a separate legacy reference; see [the original discussion](ap700-protocol.md). No AP700 image or updater is distributed here.

## Evidence needed for a conclusive answer

1. Record board silkscreen and chip top markings for a Dongle, AP9X module/STM board, and Controller X to resolve exact silicon and board revisions.
2. Obtain full flash dumps or boot logs including ROM/U-Boot banners and partition tables for the Linux devices. Update payloads omit the bootloader, so they cannot prove whether the installed bootloader accepts unsigned images.
3. Read AP9X STM32L4 option bytes through a supported non-destructive interface, if available, to establish RDP/WRP and boot settings. Do not infer them from the firmware file.
4. Identify the Controller X LPC part and inspect its CRP/ISP configuration using a documented non-destructive method. The `CRP DISABLE` volume name does not settle this.
5. Inspect both updater and device-side acceptance paths. A client-side MD5 check can be bypassed unless the device enforces authenticated-image verification.

Current answer: **we have not found evidence that any analyzed Kessil target enforces cryptographic secure boot.** The inspected update artifacts expose CRC/MD5 checks or no file-level signature check. This is evidence-bounded; it does not establish undisclosed ROM behavior, production fuse settings, or firmware versions outside this corpus.
